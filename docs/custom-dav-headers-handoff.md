# Per-account DAV gateway headers: Android implementation handoff

## Goal and context

Some self-hosted CalDAV/CardDAV endpoints sit behind an access gateway such as Pangolin. The gateway expects extra HTTP headers on **every** DAV request, in addition to the server's normal Basic authentication. For Pangolin, a typical pair is `P-Access-Token-Id` and `P-Access-Token`. Without them, discovery is rejected before the DAV server sees the request.

Calino web implements this for GitHub issue [#182](https://github.com/Ivan-Malinovski/calino/issues/182). Its account UI has a collapsed **Gateway access** section with repeatable Name/Value rows, masked values and a reveal control. The direct DAV client adds the headers to discovery, reads, writes and contact requests. The web version also has a `/setup` config generator and browser CORS concerns; **this repository is a standalone Kotlin/Compose Android app**, so neither of those web-specific pieces should be copied here. Android's native OkHttp transport has no browser CORS preflight.

This document is an implementation brief for the Android app, not an implementation or an account configuration containing real secrets.

## Intended behavior

1. A user can add zero or more custom name/value headers while connecting an account. The section is optional, collapsed when empty, and named **Gateway access** (subtitle: “For protected CalDAV servers”). Each row has Name, masked Value, reveal/hide and remove controls. Match the Android app's Compose component vocabulary, motion, accessibility semantics and 44 dp touch targets; the web implementation is a behavior/design reference, not a pixel specification.
2. A failed Connect attempt leaves the entire draft, including headers, editable. Validation appears on Connect. Reject blank/incomplete rows, duplicate names ignoring case, invalid names, empty values, and values containing CR, LF or NUL. Keep value whitespace intact because secrets may be whitespace-sensitive. Do not echo values in errors.
3. After connection, an account can **view header names and masked values, add, replace and remove rows** without removing/reconnecting the account. Changes take effect for the next discovery/sync/write, including background work and durable queue replay. Provide a clear save/error state. Never show a raw value by default, and do not put secret values in Compose saved instance state, accessibility descriptions, analytics or logs.
4. Header sets belong to one account. Reconnecting the same server/username with a new set replaces that account's old set. Removing an account deletes its headers. Existing accounts migrate to an empty set and behave exactly as before.
5. Apply headers to direct requests for both CalDAV and CardDAV: initial `/.well-known`/principal/home/collection discovery, `PROPFIND`, `REPORT`, resource `GET`, conditional `PUT`/`DELETE`, ETag probes, incremental sync, foreground refresh, WorkManager background refresh and queued writes. Preserve `Authorization`, `Depth`, `Content-Type`, `If-Match` and `If-None-Match` generated by the DAV code. A gateway may deny even the initial probe if the headers are absent.
6. A configured gateway header is a secret. Send it only to the configured account origin (scheme, host and port). Require the final DAV URL when a gateway redirects. Block cross-origin DAV hrefs and redirects before transmitting the headers; also reject same-origin redirects for requests with custom headers, with an actionable message to use the final DAV URL. Existing accounts with no custom headers must retain today's redirect/discovery behavior. Never send these headers to AI/photo import, release checks, webcal or unrelated HTTP clients.

`CredentialStore.save/load` currently handles a `DavCredentials(username, password)` object, and `KeystoreCredentialStore` encrypts only the password. Extending that credential object or introducing an adjacent `AccountDavSecrets` value is reasonable, but all callers and test doubles must use the same secure source. Do not introduce a second plaintext preference store. `CalDavAccountJson` should remain a nonsecret account index. Plan for an update operation that **preserves the password** when changing headers, and a keystore failure that does not silently make a partly saved account look usable.

`DavHttp` currently sets caller-supplied protocol headers, then Basic `Authorization`, and uses an OkHttp client with `followRedirects(true)` and `followSslRedirects(true)` because well-known discovery uses redirects. For header-bearing accounts, refuse redirects **before the next request** and surface the final-URL guidance. Do not globally disable redirects for accounts without headers. If rejecting the first 3xx response, capture `Location` only for a safe error message; do not include credentials or secret header values in that message. Validate DAV response hrefs before sending any subsequent request. Existing fetcher logic already checks some href origins; extend/centralize this for the gateway header invariant.

The current add-account sheet discovers first, then `CalinoContainer.onAccountConnected(form, calendars)` persists the account and calls `CalDavConnectionManager.onAccountConnected(account, form.password)`. Discovery uses a `CalDavForm`; ensure its headers are available during that **first** probe, not only after `onAccountConnected`. The existing account surface currently has no credential editing flow; adding header edit affordance is part of this feature.

## Transport and storage decisions

- Treat names as case-insensitive for uniqueness and reserved-name checks. Use RFC HTTP token characters: `!#$%&'*+-.^_`, the backtick character, `|~`, and ASCII letters/digits; validate before OkHttp sees the name. Store a stable representation, and do not let a custom name overwrite protocol-controlled headers.
- Preserve every value exactly as entered, apart from rejecting empty and CR/LF/NUL. Never log request headers, whole credential objects or the editor draft. Avoid copying values into saved instance state or unencrypted account serialization.
- Determine the allowed origin from the user-entered, normalized account URL. Scheme changes (`http` to `https`) and port changes count as origin changes. With headers present, tell the user to enter the final **HTTPS** DAV endpoint where possible. Android need not implement the web client's CORS diagnostics.
- Header updates should be account scoped and atomic from the user's perspective. If saving to Keystore fails, keep the old usable configuration and show an error. New header values should be used by future syncs and queue replay; in-flight requests may finish under the prior snapshot.
- Do not alter Android network security policy to permit cleartext globally. Existing server URL policy still applies; custom headers should not weaken it.

## Acceptance and verification

1. Unit tests: header validator accepts normal gateway names, rejects duplicates in mixed case, reserved names, malformed names, blank values and CR/LF/NUL; it preserves exact valid values.
2. Credential tests: legacy credentials load with no headers; save, load, replace and clear round-trip the set; account JSON and `toString()` contain no secret. Test Keystore-backed behavior with an Android test where feasible, and use `InMemoryCredentialStore` for JVM repository tests.
3. MockWebServer/OkHttp tests: initial discovery sends both gateway headers and Basic auth; `PROPFIND`, `REPORT`, `GET`, conditional `PUT`/`DELETE` all receive them; protocol headers cannot be overridden. With headers, same-origin and cross-origin redirects stop before the follow-up request, and a cross-origin DAV href is rejected before a request. Without headers, existing well-known redirects still work.
4. Connected flow: a local gateway requiring `P-Access-Token-Id` and `P-Access-Token` returns 403 when absent; adding both connects and loads calendars and contacts. Edit one value, restart the app, refresh and write a record, then remove the account and verify no secret remains. Include a background/queued-write path with the updated values.
5. Compose UI tests/screenshots: section is calm and collapsed by default, opens accessibly, masks values, reveals only on request, survives failed Connect with draft intact, and offers editing on an existing account. Verify narrow phones and large font scales with no clipping. Avoid exposing values through semantics when masked.
6. Run the Android repository's required focused Gradle checks, then the broader checks specified by `AGENTS.md`/`HANDOFF.md`. Document any emulator or live-server limitation accurately.

Use the native Android architecture above rather than porting browser fetch, Vite config or Capacitor Java code.
